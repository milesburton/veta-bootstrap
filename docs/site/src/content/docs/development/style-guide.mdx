## Typography

Pick one approach and document it here, whatever it ends up being: a single font stack for density, a heading scale for a content-heavy site, a monospace-everywhere convention for a data-dense tool. This section exists so the choice is written down once instead of re-decided per component.

```css
font-family: system-ui, -apple-system, sans-serif;
```

## Theme variants

If you support more than one theme (dark, light, high-contrast), redefine every token above per theme rather than assuming the default. Components should always read a token, never hardcode an RGB triplet; a hardcoded value breaks silently in every other theme.

## Using tokens in code

**CSS custom properties** (works everywhere: Tailwind, plain CSS, inline styles):

```css
.card {
  background: rgb(var(--gray-800));
  border: 1px solid rgb(var(--gray-700));
  color: rgb(var(--gray-100));
}
```

**Raw values at runtime** (canvas, inline SVG `fill=`, anything that needs a real string, not a CSS declaration):

```ts
function rgb(name: string, alpha = 1): string {
  const raw = getComputedStyle(document.documentElement).getPropertyValue(name).trim();
  const triplet = raw.replace(/ /g, ", ");
  return alpha === 1 ? `rgb(${triplet})` : `rgba(${triplet}, ${alpha})`;
}

rgb("--semantic-success");
```

Read the live CSS variable on each access rather than caching a resolved value in a module-level constant, so the result follows a theme switch.

## Docs site tokens

The Astro docs site (this site) keeps its own copy of the palette in `docs/site/src/styles/custom.css`. If your app has a separate frontend, decide up front whether the two stay identical (simplest: literally the same file, symlinked or copied by a build step) or are allowed to diverge (cheaper short-term, but the docs site's swatches will silently stop describing the app's actual colours unless something checks for drift). Whichever you choose, say so on this page, since the wrong assumption here is exactly the kind of thing that goes unnoticed for months.
